# 테스트 케이스 추출 — 스펙에서 무엇을 테스트할지 뽑는다

스펙 문서에서 어떤 테스트 케이스가 필요한지 뽑아내는 절차를 다룬다: 책임 단위 분해, 스펙-코드 간극 처리, 추출 4단계, 스펙 변경 대응, 생성을 건너뛰는 경우.

## 목차

1. **역할** — 테스트 케이스 추출이 답하는 질문
2. **책임 단위로 스펙 기준 분해하기** — 승인 기준 ≠ 테스트 케이스
3. **스펙-코드 간극 다루기** — TDD에서 미구현 스펙을 스켈레톤화하는 법
4. **테스트 케이스 추출 절차** — 스펙 읽기부터 스켈레톤 작성까지 4단계
5. **스펙 변경 다루기** — 기존 테스트를 스펙 변경에 맞춰 갱신하는 절차
6. **테스트 생성을 건너뛰는 경우** — 순수 데이터 객체와 인프라 트리거

---

## 1. 역할

테스트 케이스 추출은 "이 마일스톤을 검증하려면 어떤 테스트 케이스가 필요한가?"에 답한다.

출력물은 테스트 스켈레톤이다 — 기대 행동을 명확히 설명하는 이름을 가진 빈 테스트 메서드다. 실제 구현자는 나중에 테스트 코드를 채운다.

이것이 진짜 TDD를 가능하게 한다: 구현 이전에 RED 테스트가 이미 존재한다.

## 2. 책임 단위로 스펙 기준 분해하기

### 규칙

```
SPEC ACCEPTANCE CRITERIA ≠ TEST CASES

각 승인 기준을 클래스 책임 단위로 분해한다.
각 조각을 알맞은 테스트 레벨에 배치한다.
```

승인 기준 하나를 그대로 테스트 케이스 하나로 옮기면, 실제로는 서로 다른 클래스의 책임이 한 테스트에 뒤섞인다. 먼저 물어야 할 질문은 "스펙이 X라고 했으니 이 클래스에서 X를 테스트한다"가 아니라 "X가 정말 이 클래스의 책임인가?"다.

### 🚨 위험 신호

| 생각 | 실제 |
|----------------------------------------------|----------------------------------------------------------------------------------|
| "스펙이 X라고 했으니, 이 클래스에서 X를 테스트한다" | 물어라: X가 이 클래스의 책임인가? |
| "승인 기준 하나 = 테스트 케이스 하나" | 먼저 클래스 책임 단위로 분해한다 |
| "Facade 테스트는 모든 결과를 검증해야 한다" | Facade는 오케스트레이션을 검증한다. 개별 결과는 그것을 소유한 클래스의 몫이다 |

### 분해 예시

**스펙**: "주문 시 포인트가 차감되고, 재고가 줄고, 주문이 생성된다"

| 책임 | 클래스 | 테스트 레벨 | 검증할 것 |
|-------------------------|--------------------|-------------|--------------------------------------------|
| 포인트 차감 로직 | Point (도메인) | Unit | `deduct()`가 정확히 계산하는가 |
| 재고 감소 로직 | Stock (도메인) | Unit | `decrease()`가 정확히 계산하는가 |
| 오케스트레이션 성공 | OrderFacade | Integration | 시나리오가 완료되고 DB가 최종 상태를 반영하는가 |
| 트랜잭션 롤백 | OrderFacade/Service | Integration | 실패 시 모든 자원이 복구되는가 |

**규칙**: 도메인 로직의 정확성 → Unit Test. DB에 반영된 시나리오 결과 → Integration Test.

> 조합이 8개를 넘으면 `./test-data-design.md`의 조합 폭발 대응 절차 1단계(책임 분리)를 먼저 적용해 책임 분리 여부부터 검증한다.

## 3. 스펙-코드 간극 다루기 (TDD 필수)

스펙이 아직 구현되지 않은 기능을 설명할 때:

```
구현 이전에 테스트를 먼저 쓰는 TDD 워크플로인가?
├── Yes → 스펙 요구사항에 대한 스켈레톤을 생성한다 (RED 단계)
│         이 테스트는 구현이 존재하기 전까지 실패해야 정상이다
└── No  → 간극을 문서화하고 명확화를 요청한다
```

**핵심 원칙**: TDD에서 테스트는 코드가 존재하기 전에 작성된다. 구현이 아직 없더라도 모든 스펙 요구사항에 대한 스켈레톤을 생성한다.

## 4. 테스트 케이스 추출 절차

### 1단계: 스펙 레퍼런스 읽기

마일스톤 지시에 명시된 스펙 섹션을 읽고 테스트 가능한 요구사항을 모두 추출한다.

- 강제되어야 하는 비즈니스 규칙
- 정확해야 하는 계산
- 허용되거나 금지되어야 하는 상태 전이
- 처리되어야 하는 에러 조건
- 수치 제약과 그 경계(최소, 최대, 임계값)
  → 경계마다 3개의 테스트 값을 만든다: boundary-1, boundary, boundary+1
- 입력 차원과 그 동등 클래스
  → 클래스마다 대표 테스트 값 1개를 만든다
- 다중 조건 상호작용 지점
  → 결과를 결정하기 위해 조합되는 조건들은 체계적인 조합이 필요하다

값 선택의 구체적 기법(BVA·ECP·Decision Table)은 `./test-data-design.md`에서 다룬다.

### 2단계: 테스트 레벨 결정

각 요구사항이 어느 레벨(Unit, Integration, Concurrency, Adapter, E2E, Batch)에 속하는지 결정한다. 레벨 분류 기준은 `./test-levels.md`를 참고한다.

### 3단계: 레벨별 케이스 추출

해당 레벨별 레퍼런스 문서의 추출 패턴을 따른다.

### 4단계: 테스트 스켈레톤 작성

각 케이스를 BDD 구조를 따르는 테스트 메서드로 작성한다. 구조와 네이밍 규칙은 `./test-authoring.md`에서 다룬다.

- `@DisplayName`은 한국어로 행동을 설명
- Given/When/Then 주석을 구현 힌트로
- 모든 테스트 본문에 `fail("Not implemented")`

## 5. 스펙 변경 다루기

마일스톤이 기존 기능의 변경을 지시할 때:

1. 갱신된 스펙 섹션을 읽는다
2. 영향받는 범위의 기존 테스트 파일을 읽는다
3. 각 기존 테스트 케이스를 갱신된 스펙과 비교한다:
    - 이 케이스에 대해 스펙이 변하지 않았다 → 케이스를 유지한다
    - 이 케이스에 영향을 주는 스펙이 변경되었다 → 갱신된 Given/When/Then으로 다시 작성한다
    - 스펙상 더 이상 유효하지 않은 케이스 → 출력에서 제거한다
4. 갱신된 스펙이 요구하는 새 케이스를 식별한다 → 새 스켈레톤을 추가한다

출력의 모든 케이스는 `fail("Not implemented")`를 포함하는 동일한 스켈레톤 형식을 쓴다.

핵심 작업은 스펙-테스트 비교를 근거로 **무엇을 테스트할지 판단하는 것**이다.

## 6. 테스트 생성을 건너뛰는 경우

### 행동 없는 순수 데이터 객체

- **Command** — 유스케이스 입력(예: `CreateOrderCommand`)
- **Event** — 불변 사실 기록(예: `OrderCreatedEvent`)
- **DTO / Request / Response** — 데이터 전달 전용

### 비즈니스 로직 없는 인프라 트리거

- **Scheduler** — 서비스 메서드만 호출하는 `@Scheduled` 메서드
    - Scheduler의 책임은 "무엇을 할지"가 아니라 "언제 호출할지"뿐이다
    - 호출되는 서비스 메서드를 대신 테스트한다(Integration Test)
    - Cron 표현식의 정확성은 Spring Framework의 책임이다
