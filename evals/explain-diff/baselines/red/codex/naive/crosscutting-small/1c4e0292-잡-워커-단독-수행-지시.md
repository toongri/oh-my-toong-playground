# 잡 워커가 하위 에이전트를 만들지 않도록 프롬프트를 보강한 변경

## 한눈에 보기

이 변경은 잡(job)으로 실행되는 조언·리뷰 워커에게 **자신의 의견 또는 분석을 직접 완결하고, 다시 하위 에이전트를 만들지 말라**고 지시한다. 실행 코드나 잡의 생성 방식은 바꾸지 않았다. 워커가 받는 역할 프롬프트 7개에 한 줄씩 추가하거나, 기존의 “위임해도 된다”는 문장을 “위임하지 말라”로 바꾼 변경이다.

- 대상 커밋: `1c4e0292` (`chore: 잡 워커 프롬프트에 단독 수행 지시 추가`)
- 비교 범위: `1c4e0292^..1c4e0292`
- 변경 파일: 프롬프트 Markdown 7개
- 변경되지 않은 것: TypeScript 실행 로직, YAML 설정, 테스트

## 왜 필요한가

잡 워커는 상위 에이전트가 이미 만들어 놓은 작업 단위 안에서 실행된다. 이 워커가 다시 하위 에이전트를 만들면 작업 구조가 다음처럼 한 단계 더 깊어진다.

```text
상위 호출자
  └─ 잡 워커
       └─ (이전에는 가능했던) 하위 에이전트
```

이 추가 분기는 비용과 대기 시간을 늘리고, 상위 호출자가 기대한 “워커 한 명의 독립적인 의견”도 흐릴 수 있다. 이번 변경 뒤의 의도된 구조는 아래와 같다.

```text
상위 호출자
  └─ 잡 워커 ── 직접 분석·의견·리뷰를 한 번의 응답으로 반환
```

즉, 여러 관점이 필요하면 **상위 계층이 여러 워커를 명시적으로 시작**하고, 각 워커는 자기 몫만 수행한다.

## 실제 실행 흐름에서 프롬프트가 쓰이는 위치

각 스킬의 `scripts/worker.ts`는 공통 `runOneTurn()`에 해당 스킬의 `prompts` 디렉터리를 넘긴다. 예를 들어 `skills/slides-review/scripts/worker.ts:90-101`가 `promptsDir`를 전달한다.

공통 함수 `assemblePrompt()`는 다음 순서로 역할 프롬프트를 고른다.

1. 워커 이름과 같은 파일: `prompts/{worker-name}.md`
2. 없으면 기본 파일: `prompts/default.md`
3. 기본 파일도 없으면 사용자가 보낸 원문 프롬프트만 사용

선택한 파일은 `<system-instructions>` 안에 넣고, 이어서 “헤드리스 파이프라인이므로 완전한 분석을 직접 응답하라”는 공통 지시와 실제 요청을 붙인다. 이 조립 규칙은 `lib/worker-utils.ts:101-161`에 있다.

따라서 이번에 바뀐 Markdown은 설명용 문서가 아니라, 잡 워커가 실제로 받는 시스템 지시의 일부다.

## 무엇이 바뀌었나

| 스킬 / 파일 | 추가·교체된 지시 | 이 지시가 적용되는 역할 |
|---|---|---|
| `agent-council/prompts/codex.md` | “자기 관점만 논증하고 하위 에이전트를 만들지 말라” | Codex 역할 템플릿 |
| `agent-council/prompts/glm.md` | 같은 단독 논증 지시 | GLM 역할 템플릿 |
| `agent-council/prompts/gpt.md` | 단독 논증을 명시하고, 기존의 “위임하면 기다려라” 문장을 제거 | GPT 역할 템플릿 |
| `agent-council/prompts/default.md` | 단독 논증을 명시 | 이름별 템플릿이 없을 때의 기본 역할 |
| `design-review/prompts/default.md` | “이 리뷰를 혼자 수행하고 하위 에이전트를 만들지 말라” | 설계 리뷰 워커 기본 역할 |
| `diagnose/prompts/default.md` | “이 분석을 혼자 수행하고 하위 에이전트를 만들지 말라” | 진단 워커 기본 역할 |
| `slides-review/prompts/gemini.md` | “이 덱을 혼자 리뷰하고 하위 에이전트를 만들지 말라” | Gemini 슬라이드 리뷰 역할 |

`agent-council`의 역할별 템플릿은 같은 원칙을 역할에 맞게 표현한다. 예를 들어 구현 현실성을 담당하는 Codex 역할은 “자기 관점만 논증하라”, 대안 탐색 역할인 GLM도 독립 의견을 내라고 한다. 반면 `design-review`와 `diagnose`는 각각 **리뷰**와 **분석**을 혼자 수행하라고 말한다.

## 전후 차이

### 이전

`gpt.md`, `design-review/prompts/default.md`, `diagnose/prompts/default.md`에는 한 번의 응답으로 끝내라는 지시는 있었지만, 하위 작업을 위임하는 것 자체는 허용했다. 단, 위임했다면 같은 턴에서 완료될 때까지 기다리라고만 했다.

```text
위임 가능 → 하위 작업을 전면에서 끝까지 기다림 → 하나의 응답으로 반환
```

나머지 네 프롬프트에는 하위 에이전트에 관한 명시적 지시가 없었다.

### 이후

모든 변경 대상 프롬프트는 위임을 수행 방식으로 선택하지 못하게 한다.

```text
하위 에이전트 생성 금지 → 워커가 직접 판단 → 하나의 완결된 응답으로 반환
```

특히 세 파일에서는 의미가 단순한 문구 추가보다 크다.

- `agent-council/prompts/gpt.md`: “위임할 경우”라는 허용 문장을 제거했다.
- `design-review/prompts/default.md`: 같은 허용 문장을 “리뷰를 혼자 수행”으로 교체했다.
- `diagnose/prompts/default.md`: 같은 허용 문장을 “분석을 혼자 수행”으로 교체했다.

## 프롬프트 지시와 실행 차단은 다르다

이번 커밋이 추가한 것은 **프롬프트 수준의 행동 지시**다. 모델이 지시를 따라야 한다는 뜻이지, 모든 경로에서 도구가 물리적으로 사라진다는 뜻은 아니다.

이 저장소에는 별도의 **실행 수준 차단**도 이미 있다. `design-review`와 `diagnose`의 설정은 `settings.deny.subagents: true`를 선언한다. 공통 잡 코드가 이를 읽어 CLI별 제한으로 바꾼다.

| 워커 CLI | 기존 실행 수준 처리 | 근거 |
|---|---|---|
| Codex | `agents.enabled=false`를 전달해 하위 에이전트 도구 설명 자체를 제거 | `lib/generic-job.ts:416-426` |
| Claude | `Agent`와 이전 이름인 `Task` 도구를 권한 거부 목록에 넣음 | `lib/generic-job.ts:427-447` |
| OpenCode | `permission.task`를 `deny`로 설정 | `lib/generic-job.ts:448-489` |

따라서 현재 `design-review`와 `diagnose`는 **프롬프트 지시와 실행 차단을 함께** 사용한다. 각각의 선언은 `skills/design-review/design-review.config.yaml:19-24`, `skills/diagnose/diagnose.config.yaml:14-19`에서 확인할 수 있다.

반대로 이 범위에서 확인한 `agent-council/council.config.yaml`과 `slides-review/review.config.yaml`에는 `deny.subagents: true`가 없다. 그러므로 이 두 스킬에 대한 이번 커밋의 보호는 프롬프트 지시다. 특히 `slides-review`는 Gemini를 사용하며, 공통 잡 코드는 Gemini에 대한 실행 차단 수단이 없으면 deny 설정을 가진 잡을 시작하지 않도록 한다(`lib/generic-job.ts:162-193`, `491`).

## 적용 범위를 읽을 때 주의할 점

“프롬프트 파일을 바꿨다”와 “현재 모든 실행 워커가 그 파일을 쓴다”는 같은 말이 아니다.

현재 `agent-council/council.config.yaml:20-41`에 선언된 멤버는 `claude`, `gpt`, `glm`이다. 이 중 이번에 바뀐 것은 `gpt.md`와 `glm.md`다. `codex.md`도 변경됐지만 현재 설정에는 `codex`라는 멤버가 없으므로, 해당 이름으로 워커를 구성할 때 적용되는 역할 템플릿이다. 또한 `default.md`는 이름별 파일을 찾지 못했을 때의 폴백이다.

한편 현재 `claude.md`에는 이번 단독 수행 문구가 추가되지 않았다. 따라서 이 커밋만 놓고 보면 Council의 기본 구성에서 Claude 역할까지 같은 프롬프트 지시가 확장됐다고 말할 수는 없다. 이 문서는 설정과 역할 파일을 직접 대조한 결과를 구분해 설명한다.

## 사용 예시

설계 선택에 대한 Council 잡을 상위 호출자가 시작했다고 가정하자.

```text
질문: “동기 처리와 비동기 처리 중 어느 쪽이 적절한가?”

상위 호출자
  ├─ GPT 워커: 구현 비용·위험을 직접 분석
  ├─ GLM 워커: 가정을 의심하고 대안을 직접 분석
  └─ (필요하다면) Claude 워커: 트레이드오프를 직접 분석

상위 호출자: 세 응답을 읽고 종합
```

이번 변경의 핵심은 GPT·GLM 등 변경된 역할이 “추가 조사원을 만들고 결과를 기다리는” 방식으로 자신의 답변을 구성하지 않는다는 점이다. 종합 책임은 계속 상위 호출자에게 있다.

## 영향과 비영향

### 기대 효과

- 워커 내부의 재귀적 팬아웃 가능성을 줄인다.
- 워커별 역할과 책임 경계가 더 분명해진다.
- 워커 응답이 하위 작업 완료에 매달리는 상황을 줄인다.
- 이미 있는 한 턴 완결 지시와 일관된 방향이 된다.

### 이 커밋만으로 바뀌지 않는 것

- 잡을 몇 개 시작할지, 어떤 모델을 선택할지는 바뀌지 않는다.
- 상위 호출자의 결과 수집·종합 책임은 바뀌지 않는다.
- TypeScript의 프롬프트 조립, 워커 실행, 상태 저장 로직은 바뀌지 않는다.
- 모든 스킬·모든 CLI에 강제 차단이 새로 생기는 것은 아니다.

## 검토 포인트

후속 변경을 검토할 때는 아래를 확인하면 된다.

1. 새 워커 역할 파일을 추가한다면, 그 역할도 단독 수행 원칙이 필요한가?
2. 프롬프트 지시만으로 충분한가, 아니면 해당 CLI에서 `deny.subagents: true`를 실행 수준으로도 강제할 수 있는가?
3. 설정의 실제 멤버 이름과 `prompts/{name}.md` 파일 이름이 맞는가? 맞지 않으면 `default.md`가 사용된다.
4. 역할에 맞는 독립성인가? Council 멤버는 자기 관점만 내고, 최종 종합은 상위 호출자가 맡아야 한다.

## 퀴즈

### 1. 객관식

이번 커밋이 직접 변경한 것은 무엇인가?

1. 잡 생성 TypeScript 로직
2. 워커 역할 프롬프트 Markdown
3. 워커 모델 목록 YAML
4. 테스트 코드

### 2. 단답형

`assemblePrompt()`가 역할 프롬프트를 찾는 우선순서를 세 단계로 쓰세요.

### 3. 객관식

`design-review`와 `diagnose`에서 프롬프트 지시 외에 하위 에이전트 생성을 막는 기존 장치는 무엇인가?

1. `settings.deny.subagents: true`
2. 워커 타임아웃을 0으로 설정
3. 모든 MCP 서버 제거
4. 결과 파일을 읽기 전용으로 설정

### 4. O/X

현재 `agent-council` 설정의 모든 멤버 역할 파일에는 이번 커밋으로 단독 수행 지시가 추가됐다.

### 5. 서술형

이번 변경 뒤에도 Council의 최종 종합을 워커가 아니라 상위 호출자가 맡아야 하는 이유를 한두 문장으로 설명하세요.

### 정답과 해설

1. **2번.** 7개의 역할 프롬프트 Markdown만 변경됐다.
2. **`prompts/{worker-name}.md` → `prompts/default.md` → 원문 프롬프트만 사용.**
3. **1번.** 공통 잡 로직이 CLI별 실행 제한으로 번역한다.
4. **X.** 현재 Council 설정의 `claude` 멤버가 쓰는 `claude.md`는 이 커밋에서 바뀌지 않았다. `gpt.md`와 `glm.md`는 바뀌었다.
5. **예시 답안:** 워커는 자신의 독립 관점만 제공하도록 역할이 분리돼 있다. 여러 관점의 공통점·차이를 비교하고 최종 권고를 만들 책임은 상위 호출자에게 남아 있다.
