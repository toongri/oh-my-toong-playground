# 트리 선택기의 수평 이동 추가

## 한눈에 보기

커밋 `068ab5d1`은 대화 세션 트리 선택기에서 **깊게 들여쓴 선택 항목의 내용을 읽을 수 없던 문제**를 고친다. 이전에는 줄 전체를 오른쪽에서 잘랐기 때문에, 트리 구조가 깊어질수록 선택한 항목의 `user:`나 `assistant:` 같은 실제 내용이 화면에 나타나지 않을 수 있었다. 이제 선택 항목의 내용 시작 위치를 기준으로 트리의 본문을 왼쪽으로 이동해, 좁은 터미널에서도 선택한 항목의 내용을 볼 수 있게 한다.

변경 파일은 다음 두 개다.

| 파일 | 역할 |
| --- | --- |
| `packages/coding-agent/src/modes/interactive/components/tree-selector.ts` | 트리 행을 수평 뷰포트에 맞춰 렌더링한다. |
| `packages/tui/src/index.ts` | 문자열을 터미널 열 단위로 자르는 `sliceByColumn` 유틸리티를 외부 패키지에 공개한다. |

## 문제: 들여쓰기가 내용을 밀어낸다

트리 선택기의 한 행은 아래처럼 구성된다.

```text
커서  트리 선·들여쓰기·접기 표시·활성 경로 표시  라벨·시간  항목 내용
›     │  └⊟  •                               [중요]    user: 요청 내용
```

기존 구현은 이 전체 행을 터미널 폭으로 잘랐다.

```ts
lines.push(truncateToWidth(line, width));
```

따라서 트리 깊이가 커지면 왼쪽의 구조 표시가 폭을 대부분 사용한다. 예를 들어 화면 폭이 24열이고 들여쓰기와 표식이 21열을 차지하면, 선택한 항목의 본문은 거의 또는 전혀 남지 않는다. 사용자는 어느 항목을 선택했는지 구조만 보고, 그 항목의 실제 메시지는 확인하기 어려웠다.

## 해결 방식: 커서는 고정하고 본문만 함께 이동한다

변경 후에는 각 행을 다음 두 영역으로 나눈다.

```text
고정 영역 (2열)        이동·잘림 영역
┌──────────────┐ ┌──────────────────────────────────────────┐
│ 선택 커서    │ │ 트리 선, 들여쓰기, 표식, 라벨, 항목 내용 │
└──────────────┘ └──────────────────────────────────────────┘
```

- 고정 영역은 선택 커서 `› ` 또는 공백 두 칸이다. 수평 이동 중에도 항상 남아 현재 선택 상태를 보여 준다.
- 이동 영역은 트리 구조와 항목 표시 영역(라벨·시간·메시지 본문)을 포함한다. 선택 행에서 트리 표식 직후의 표시 영역 시작점이 너무 오른쪽이면, **화면에 보이는 모든 행에 같은 수평 이동량**을 적용한다. 따라서 행 사이의 구조적 정렬은 유지된다.
- 이동은 선택 행에만 적용하지 않는다. 선택 행만 이동하면 트리 선과 다른 행의 위치가 달라져 트리 구조를 해석하기 어려워지기 때문이다.

### 렌더링 흐름

```text
각 가시 행 생성
  └─ cursor / body / 표시 영역 시작 열(anchorCol) / body 폭을 기록
       ↓
선택 행과 최대 본문 폭으로 horizontalScroll 계산
       ↓
각 행의 body에서 horizontalScroll 이후만 열 단위로 추출
       ↓
고정 cursor를 다시 앞에 붙이고 최종 폭으로 제한
```

`HorizontalViewportRow`는 이 계산에 필요한 `gutter`, `body`, `anchorCol`, `bodyWidth`, `isSelected`를 담는다. 기존처럼 완성된 문자열 하나를 바로 자르지 않고, 수평 뷰포트 계산에 필요한 화면상 정보를 보존하는 구조다.

## 언제, 얼마나 이동하는가

수평 이동 계산은 `renderHorizontalViewport`에 모여 있다.

1. 전체 폭에서 고정 커서 2열을 제외해 본문 뷰포트 폭을 구한다.
   - `viewportWidth = max(0, width - 2)`
2. 현재 화면에 그릴 행 중 가장 긴 본문을 찾아, 실제로 옆으로 이동할 여지가 있는지 계산한다.
   - `maxHorizontalScroll = max(0, 가장 긴 본문 폭 - 본문 뷰포트 폭)`
3. 선택 행에서 트리 표식 직후의 표시 영역 시작점(`anchorCol`) 뒤에 최소한의 내용을 보여 줄 수 없을 때만 이동을 시작한다. 라벨과 시간이 있으면 실제 메시지 본문은 이 시작점보다 더 오른쪽에 있다.
4. 이동 후에도 표시 영역 시작점 앞의 문맥을 일부 남긴다. 문맥 폭은 본문 뷰포트의 약 1/4이며 2~12열 범위로 제한된다.
5. 선택 행의 표시 영역으로 보이는 폭은 본문 뷰포트의 약 1/3이며 4~20열 범위로 제한된다.

이 제한값은 매우 넓은 화면에서 필요 이상으로 많이 이동하거나, 매우 좁은 화면에서 0열 또는 과도한 문맥을 요구하지 않도록 한다. 표시 영역 시작점이 충분히 보이는 경우 `horizontalScroll`은 0이므로, 기존처럼 왼쪽부터 표시된다.

마지막 폭 제한은 `truncateToWidth(line, width, "")`로 수행한다. 세 번째 인수가 빈 문자열이므로, 이 경로에서 폭 초과로 잘릴 때는 이전 기본값인 `...`을 붙이지 않는다.

## 예시

가로 폭이 좁고 선택 항목이 깊은 위치에 있다고 가정한다.

```text
이전
› │     └─ • [분기] ...
                  ^ user: 뒤의 내용이 잘릴 수 있음

이후
›        • [분기] user: 필요한 메시지 내용...
^ 커서는 고정          ^ 선택 항목의 본문이 보임
```

이동 후에도 트리의 맨 왼쪽 전체를 항상 보장하는 방식은 아니다. 대신 현재 선택한 항목을 읽는 데 필요한 일부 트리 문맥과 메시지 내용을 함께 보여 주는 방식이다.

## 문자열 처리에서 중요한 점

수평 이동은 JavaScript 문자열 인덱스가 아니라 **터미널 열(column)** 을 기준으로 동작해야 한다. 한글·한자·이모지처럼 두 열을 차지할 수 있는 문자와 ANSI 색상 제어 코드가 있기 때문이다.

이를 위해 `@earendil-works/pi-tui`의 `sliceByColumn`을 사용한다.

```ts
sliceByColumn(row.body, horizontalScroll, viewportWidth, true)
```

- 시작 위치와 길이를 화면 열 단위로 지정한다.
- ANSI 색상 코드는 화면 폭으로 세지면서도, 잘라낸 결과의 스타일은 유지한다.
- 마지막 인수 `true`는 폭 2열 문자가 뷰포트 경계를 넘어가면 그 문자를 제외한다. 그 결과 최종 행이 지정 폭을 넘지 않는다.
- 잘라낸 본문 뒤에는 ANSI reset 코드(`\x1b[0m`)를 붙인다. 잘린 위치에서 선택 배경색이나 글자색이 다음 렌더링으로 새지 않도록 하기 위함이다.

원래 `sliceByColumn`은 TUI 패키지 내부에서 이미 사용되고 있었다. 이번 변경은 coding-agent 패키지에서도 이 유틸리티를 가져올 수 있도록 `packages/tui/src/index.ts`에서 재수출한다. 새 문자열 자르기 로직을 중복 구현하지 않은 점이 핵심이다.

## 코드 수준의 전후 비교

| 관점 | 이전 | 이후 |
| --- | --- | --- |
| 행 조립 | 커서부터 본문까지 하나의 `line` 문자열 | 고정 `gutter`와 이동 가능한 `body`를 분리 |
| 폭 제한 | 전체 행의 오른쪽을 잘라며 기본적으로 `...` 표시 | 선택 행의 표시 영역 시작점을 기준으로 `body`를 수평 이동한 뒤, 생략 부호 없이 최종 제한 |
| 선택 배경 | 전체 `line`에 적용 | `gutter`, `body` 각각에 적용해 분리 후에도 같은 배경 유지 |
| 문자 폭 | `truncateToWidth`로 끝부분만 제한 | `sliceByColumn(..., true)`로 시작 열부터 안전하게 추출한 뒤 최종 제한 |
| 패키지 경계 | `sliceByColumn`은 TUI 내부용 | TUI 진입점에서 재수출하여 coding-agent가 사용 |

## 영향과 확인 사항

- 사용자에게 보이는 영향은 트리 선택기 렌더링뿐이다. 탐색, 필터, 접기, 선택 처리의 데이터 구조와 키 입력 동작은 이 커밋에서 바뀌지 않았다.
- 선택 행이 충분히 왼쪽에 있거나 화면이 넓으면 수평 이동은 발생하지 않는다.
- 수평 이동량은 현재 화면에 렌더링되는 행들의 최대 폭을 사용하므로, 화면에 동시에 보이는 트리 행은 같은 기준선으로 이동한다.
- 커밋의 변경 목록에는 자동화 테스트 파일이 포함되지 않았다. 따라서 이 변경 자체에 대한 새 회귀 테스트는 추가되지 않았다.

## 퀴즈

1. 이전 구현에서 깊은 트리의 선택 항목 본문이 보이지 않을 수 있었던 직접적인 이유는 무엇인가?
2. 수평 이동 중에도 항상 고정해서 보여 주는 2열 영역은 무엇인가?
3. 수평 이동을 선택 행 하나에만 적용하지 않고 가시 행 전체에 동일하게 적용하는 이유는 무엇인가?
4. `sliceByColumn(..., true)`의 `true`는 폭 2열 문자 경계에서 어떤 문제를 막는가?
5. 선택 행의 표시 영역 시작점이 이미 충분히 보일 때 `horizontalScroll`의 값은 무엇인가?

### 정답

1. 커서·트리 들여쓰기·표식·본문을 하나의 문자열로 만든 뒤, 전체 행의 오른쪽을 잘랐기 때문이다.
2. 선택 커서 `› ` 또는 비선택 행의 공백 두 칸으로 이루어진 `gutter`다.
3. 모든 행의 정렬과 트리 구조의 상대 위치를 유지하기 위해서다.
4. 한글·한자·이모지 같은 폭 2열 문자가 뷰포트 끝을 넘어 최종 행 폭을 초과하는 문제를 막는다.
5. `0`이다. 이때는 수평 이동 없이 왼쪽부터 렌더링한다.
