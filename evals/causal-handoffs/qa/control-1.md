- **actor**: 인증된 API 클라이언트 U7. 환불 HTTP endpoint에 curl로 요청하며, 주문 소유자가 viewer 역할로 환불을 시도한다.
- **preconditions**: QA seeder로 기존 성공 요청 직전 상태의 독립 복사본 두 개를 준비한다. 각각 U7 소유의 결제된 O17, 환불 가능 잔액 700, 요청 금액 700, 미사용 K7이며 기존 R9와 provider/ledger 이력은 포함하지 않는다. 두 복사본에서 신원·소유권·금액·키·환경은 같고 역할만 owner/viewer로 다르게 설정한다.
- **steps**: 각 복사본의 초기 상태와 실제 인증 역할을 확인한다. owner 복사본에서 U7로 O17에 금액 700, K7 환불 요청을 한 번 보낸다. 독립된 viewer 복사본에서도 동일 요청을 한 번 보낸다. 요청과 수신 HTTP 상태·본문을 보존하고, 각 복사본의 잔액 및 provider 환불·ledger debit 전후 변화를 확인한다.
- **expected**: owner 요청은 새 환불을 반환하고 provider 환불 1회, ledger debit 1회, 잔액 0이 된다. viewer 요청은 권한 거부 응답을 반환하며 환불을 생성하지 않고 provider 환불·ledger debit 증가 0, 잔액 700을 유지한다.
- **why-needed**: 변경된 역할 검사만 분리해 검증하는 자동 e2e가 없다. 준비된 U8/900/K7 사례는 소유권 불일치, 잔액 초과, 기존 키 재사용이 섞여 있어 역할 검사가 고장 나도 거부되거나 기존 R9가 반환될 수 있다. 준비 시간과 리뷰 마감은 이 모호성을 해소하지 못한다.
- **priority**: H — 결제 권한 우회와 금전 변경 위험.

근거 해석: 위 결과는 수집 예정이며 아직 실행하지 않았다. 두 독립 요청에서 역할만 달라 성공과 권한 거부가 갈리면, 이 소유자·금액·신규 키 조건에서 viewer 제한이 작동한다는 근거가 된다. 응답에 provider/ledger 전후 관찰을 보강해야 무변경도 입증된다. 소유권 검사, 초과 금액 거부, 재전송 처리 전체의 정확성까지 입증하지는 않는다.
